# 图片压缩与本地优先保存（0.2.7）

## 已确认的问题

用户提供的错误为 `runtime.sendMessage: Message exceeded maximum allowed size of 64MiB`，失败发生在弹窗向后台发送消息时，尚未上传 GitHub。旧数字数组和重复主图会膨胀消息；0.2.5 改为 Base64 后减少了体积，但大量图片仍可能超过消息限制。

## 当前处理流程

1. 手动选图和粘贴保留原始图片作为草稿；提交时仅对原图大于 2 MiB（2 × 1024 × 1024 字节，界面显示 2 MB）的图片尝试 JPEG 编码，质量 90%，保留原尺寸。等于阈值不压缩。
2. “本次不压缩图片”是整个弹窗会话的总开关：勾选后，本次提交的所有手动上传和粘贴图片都使用原图，包括勾选前已添加的图片。开关不写入草稿或设置，重新打开弹窗恢复默认；页面提取始终不受影响。未勾选时，只有 JPEG 比原文件更小才采用。JPEG 有损，透明区域以白色填充。
3. 草稿图片仍保存到草稿 IndexedDB。提交时另存到独立的 `infoflow-picker-sync-images` 数据库，保存自有二进制字节和 MIME 类型。
4. 完成本地图片事务后，弹窗仅发送 `storageId` 和类型；同步队列也只保存引用。队列持久化成功才提示已保存。
5. 后台从本地图片库读取，上传 GitHub。失败保留数据供重试；成功或用户取消任务后清理图片。清空草稿不会删除待上传图片。
6. 页面提取继续兼容 Base64 和 URL。已有二进制同样存本地；只有 URL 的图片仍由后台下载。页面图片不会强制进行 JPEG 压缩。
7. JPEG 输出使用 `.jpg` 后缀，PNG 使用 `.png`，其他已知类型使用对应后缀。JSON / Markdown 字段保持兼容。

## 验证

- `npm test`：10 项回归测试，覆盖混合来源、主图索引、旧队列、队列预览、上传边界及本地写入失败。
- `scripts/verify-images-browser.mjs`：真实 Chrome 的 Canvas 与 IndexedDB 验证。需要可用的 Playwright；可通过 `PLAYWRIGHT_MODULE` 指定模块路径，通过 `CHROME_PATH` 指定 Chrome。
- 测试样本从 3,608,726 字节压缩到 864,888 字节，1024 × 1024 尺寸保持不变。具体压缩率取决于图片内容。
- 50 MiB 测试数据仅产生 120 字节的引用消息。关闭页面并清空草稿后，数据仍可读取，删除队列图片后不再可读。
- Chrome 和 Firefox 分别构建；没有向真实 GitHub 仓库上传测试图片。

本地存储仍受磁盘及浏览器配额影响；GitHub 上传也有服务端文件大小限制。新的引用机制解决图片随消息传递导致的 64 MiB 上限，不表示可无限保存图片。
