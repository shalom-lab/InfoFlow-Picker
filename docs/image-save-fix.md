# 本地上传、粘贴图片保存失败排查

## 发现的问题

本地选图和粘贴图片经过 Canvas 转为 PNG，预览使用内存中的 Data URL。旧提交代码将图片的 Base64 解码为逐字节数字数组，再写入 `browser.storage.local` 中的同步队列；同一张主图同时出现在 `image` 和 `images` 中，JSON 序列化时重复保存。

回归样本：2 MiB 图片数据（字节循环 0–255），旧结构序列化后超过 14 MiB，新结构约 2.67 MiB。这证明原来的保存路径存在明显的数据膨胀，可导致本地存储配额错误，而预览不经过队列，仍然正常。

右键采集如果提交的是图片网址，队列只保存 URL，后台下载图片，所以不受这次数字数组膨胀影响。如果右键采集取得的是 Base64，也会经过原来的问题路径；不能笼统认为所有右键图片都不会失败。右键图片没有经过本地选图的强制 PNG 转换，数据大小也可能不同。

尚未拿到用户浏览器的实际错误日志，因此不能确认本次用户遇到的全部失败均由容量引起。

## 修改

- 图片提交和队列保存使用 Base64，后台上传前恢复二进制。
- 主图只保存索引，避免重复保存主图数据。
- 兼容旧队列中的数字数组和图片网址。
- 保存失败时显示具体错误内容，不再统一提示检查设置。
- GitHub 的文件路径和 JSON / Markdown 输出格式保持原有实现，见 [数据格式文档](github-data-format.md)。

## 验证与限制

运行 `npm test`，覆盖图片在消息及 JSON 序列化后字节一致、多图主图索引、旧任务数据和 URL 下载。浏览器构建分别使用 `npm run build:chrome`、`npm run build:firefox`。

此修改减少数据体积，不取消浏览器存储配额；非常大的图片或积压的多条任务仍可能触及容量上限。测试使用模拟下载，没有向真实 GitHub 仓库写入数据。

重新加载 `dist/chrome` 或 `dist/firefox` 构建后，用原先失败的图片测试本地选图和粘贴。若仍然失败，记录新的具体错误；已进入队列的任务可展开详情查看 `lastError`。
